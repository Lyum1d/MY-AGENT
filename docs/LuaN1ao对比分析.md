# LuaN1ao（鸾鸟） vs 本项目 · 逐层架构对比

> 对比对象：`LuaN1aoAgent`（Apache-2.0，腾讯云黑客松智能渗透决赛 Top-Ranked，第三方开源项目）  
> 对比基准：本项目 `src-agent`（FastAPI + 单步 ReAct + 工具箱子进程，本地小模型优先）  
> 目的：标出**能借鉴 / 要改造 / 别抄**，并落到本项目代码。  
> 生成时间：2026-09-15

---

## 0. 先看前提差异（不看这个，下面全错）

| 前提       | 鸾鸟                                                                      | 本项目                             |
| -------- | ----------------------------------------------------------------------- | ------------------------------- |
| 模型假设     | **强云端模型**（README 明示 `LLM_PLANNER_MODEL=gpt-4o`，并注明"规划器需要强推理能力"）         | **本地小模型优先**（qwen3.5:9b），云端为可选路由 |
| 全局迭代上限   | `GLOBAL_MAX_CYCLES = 50`                                                | `MAX_STEPS = 12`（每条消息）          |
| 成本熔断     | `GLOBAL_MAX_TOKEN_USAGE = 5,000,000`（超限强杀）                              | **无**（只有单价表事后统计）                |
| 模型分工     | 四个角色各自配模型 + 各自配温度（planner 0.5 求创造 / executor 0.3 求稳 / reflector 0.2 求准） | 单一决策后端                          |
| 单次工具输出上限 | `EXECUTOR_MAX_OUTPUT_LENGTH = 50000`                                    | `MAX_OUTPUT_CHARS = 8000`       |
| 消融开关     | `EXECUTION_MODE = default / linear / react`；`NO_CAUSAL_GRAPH`           | 无                               |

**一句话结论**：鸾鸟&#x662F;**"富模型 + 富预算"**&#x67B6;构，它的 P-E-R 与图谱推理建立在"模型能稳定输出结构化 JSON、且每轮能吃下全图上下文"的前提上。  
本项目&#x662F;**"穷模型 + 严预算"**&#x67B6;构，单步 ReAct 是对模型能力的**主动让步**，不是能力缺失。  
→ 因此结论不是"谁更好"，而是"**哪些机制不依赖强模型就能搬**"。

值得一提：**鸾鸟自己也提供了 `EXECUTION_MODE=react`（纯 ReAct，关掉 Planner/Reflector）作为消融对照**——说明作者本人也把 ReAct 当作有效基线，而不是被淘汰的方案。

## 1. 规划方式

|       | 鸾鸟                                                                                              | 本项目                                                                 |
| ----- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 机制    | Planner 输出**图编辑指令**（`ADD_NODE` / `UPDATE_NODE` / `DEPRECATE_NODE`），任务建模为 **DAG**；按拓扑依赖自动识别可并行任务 | **单步 ReAct**：每轮只决定"下一步用哪个工具"，执行完把真实结果回喂再问下一步                        |
| 依据    | `core/planner.py` + `core/graph_manager.py`                                                     | `app/agent.py:452` 的单步循环                                            |
| 为什么不同 | 依赖模型稳定产出结构化 JSON                                                                                | 实测 qwen3.5:9b 被要求一次规划多步时**只输出文字、不产生 tool_calls**（见 `agent.py` 顶部注释） |

- **能借鉴**：`EXECUTION_MODE` 这种"**消融开关**"的工程习惯——把规划方式做成可切换。当本项目临时路由到云端强模型（`auto_route` 已有）时，可以启用更激进的规划模式；本地时回落单步。
- **别抄**：DAG + 图编辑指令。前提是①模型能稳定出结构化 JSON；②每次 Planner 调用都要带上**全图上下文**（很贵）。用本地 9B 模型跑这套，图会被写成幻觉。

## 2. 上下文管理 ← **差距最大的一层**

|    | 鸾鸟                                                                                  | 本项目                                         |
| -- | ----------------------------------------------------------------------------------- | ------------------------------------------- |
| 结构 | **三个角色各自独立的上下文对象**（PlannerContext / ExecutorContext / ReflectorContext）             | 单一 `session.messages` 数组，持续累积               |
| 压缩 | **LLM 摘要压缩**：`llm.summarize_conversation()` 生成 `compressed_history_summary`，再保留滑动窗口 | **无压缩**；只靠 `MAX_OUTPUT_CHARS=8000` 截断单条工具输出 |
| 触发 | 双阈值：消息数 `12` / token 数 `80000`；另有多档（保留最近 `6` 条、最小压缩 `5` 条、间隔 `5` 轮、间隔消息阈值 `8`）      | 无                                           |
| 窗口 | `PLANNER_HISTORY_WINDOW = 15`，`REFLECTOR_HISTORY_WINDOW = 15`                       | 无                                           |

**这是本项目最该补的一层**，而且它正好对应 README「已知限制 4：本地模型决策较慢、长任务会退化」和"跑十几轮就开始忘事"的真实现象。

- **要改造（不是照抄）**：保留"摘要压缩"的**思路**，但把 **LLM 摘要换成确定性裁剪**。理由：用本地小模型做摘要，摘要本身就会出幻觉，等于用一个不可靠的环节去修另一个不可靠的问题。  
  落地建议（零 token 成本、不会引入幻觉）：
  1. 保留最近 **N 轮**（建议 6）完整消息；
  2. 更早的 `role=tool` 消息替换为一行结构化摘要：`[已压缩] 工具=httpx 目标=example.com 结果=200/nginx（输出 4.2KB 已省略）`；
  3. 复现成本极低——`agent._step_dict()` 已经算好了这一步的工具名/目标/状态，`step.output[:200]` 即可当摘要；
  4. 触发条件用**估算字符数**（例如 > 40000）或消息条数（> 24），把阈值放进 `config.py`。
- **别抄**：LLM 摘要 + 三角色独立上下文（后者依赖角色分离，见 §1）。

## 3. 失败归因 ← **最值得借鉴，且不依赖强模型**

鸾鸟用一套 **L0–L5 严格递进归因**（`core/prompts/templates/zh/common/failure_attribution_levels.jinja2`）：

| 级别 | 含义                                  | 归因值                          |
| -- | ----------------------------------- | ---------------------------- |
| L0 | 来自工具的原始观察                           | —                            |
| L1 | **工具执行失败**（超时 / 命令不存在 / 语法错 / 权限不足） | `L1_TOOL_FAILURE`            |
| L2 | **前提条件失败**（会话过期 / 认证失败 / 依赖不可用）     | `INVALIDATED_PREREQUISITE`   |
| L3 | **环境干扰**（WAF 拦截 / 防火墙 / 限速 / 服务无响应） | `ENVIRONMENTAL_INTERFERENCE` |
| L4 | **假设被证伪**（参数没有注入点 / 过滤器绕不过）         | `L4_FALSIFIED`               |
| L5 | **战略层面错误**（路径选错 / 策略僵局 / 目标漂移）      | `L5_STRATEGIC_FAILURE`       |

关键规则：**只有在排除低层级原因后，才能归因到高层级**；且禁止"连续 L4 失败却提不出新假设"时继续硬打，应触发专家分析。

本项目的现状（`app/agent.py`）：所有失败都被压成一句  
`【X 执行失败】退出码 N …… 禁止用同样参数再次调用`，然后靠 `consecutive_failures >= 3` **直接停止**。

- **能借鉴（强烈推荐）**：把 L1 / L3 / L4 的**三分法**写进回喂内容，让模型知道该往哪个方向调整：
  - **L1**（启动失败/超时/进程异常）→ 该**换参数、放大超时，或换同类工具**；
  - **L3**（401/403/429/WAF 特征/被拦页）→ 该**换编码、换参数位置、或换手法**，不是换工具；
  - **L4**（请求成功 200 但没有差分）→ 该**放弃这个假设，换测试思路**。  
    实现上不需要图谱，只要在 `_execute()` 组装回喂文本时按退出码 + 输出特征打一个 `归因: L?` 标签即可。
- **为什么这条收益大**：本项目"连续 3 次失败就停"触发率高，根源就是模型分不清"是工具坏了还是我想错了"，于是反复换工具、每条都失败。给出归因标签后，它会知道该换思路而不是换工具。
- **别抄**：L5 战略重规划 + `FALSIFIES` 因果边（需要 Reflector 角色和因果图）。

## 4. 终止与预算控制

| 维度       | 鸾鸟                                                          | 本项目                                    |
| -------- | ----------------------------------------------------------- | -------------------------------------- |
| 迭代上限     | `GLOBAL_MAX_CYCLES = 50`                                    | `MAX_STEPS = 12` / 条消息                 |
| **成本熔断** | **`GLOBAL_MAX_TOKEN_USAGE = 5,000,000`**，超限"资源熔断"强杀         | **无**                                  |
| 无产出判定    | `EXECUTOR_NO_ARTIFACTS_PATIENCE = 10`（连续 10 步**没有新产出物**才停）  | 无                                      |
| 连续失败     | `EXECUTOR_FAILURE_THRESHOLD = 3` → **触发策略切换**               | `consecutive_failures >= 3` → **直接停止** |
| 无工具调用    | —                                                           | `nudges < 2` 催促 2 次后判定给出结论             |

- **能借鉴 ①（改动极小、价值高）：token 熔断。** 本项目已有 `usage_log` 表 + `usage.summary()`，加一个"本会话累计 token 超过阈值就停止并提示"即可。用云端供应商时这是**钱包保险**（当前一个失控任务能无声烧掉几十元）。
- **能借鉴 ②（直接对应"没到 12 就停"的现象）：失败阈值的语义。** 把"连续失败 3 次 → 停止"改成"连续失败 3 次 → **先换策略/换工具类**，连续失败到更高阈值（如 6）才停"。几行代码。
- **能借鉴 ③：用"无产出"替代"无成功"当判据。** 本项目已有「已证事实库」和「情报库」——把判据改成"连续 N 步既没新增事实、也没新增情报、也没有新接口入队"，比"失败次数"更贴近"是不是在白干"。
- **别抄**：50 轮 × 全图上下文的预算（成本量级不同）。

## 5. 工具层

|    | 鸾鸟                                                                                                                             | 本项目                                                                                 |
| -- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| 接入 | **MCP**（`mcp.json` 配置）：`http_request` / `shell_exec` / `python_exec` + 元认知工具 `think` / `hypothesize` / `reflect` / `halt_task` | 自建注册表 + `executor`（工具箱子进程）+ `replayer`（HTTP 重放）+ `pyexec`（代码通道）+ `kb` / `fofa` 内置工具 |
| 并发 | `asyncio.gather` 批量并行；HTTP 工具带 `concurrent_count` 参数                                                                           | 逐步串行（一步一动，有意为之）                                                                     |
| 分级 | 无风险分级；靠 README「强烈建议在 Docker / VM 中运行」+ 免责声明                                                                                    | **L0–L3 风险分级 + 授权白名单 + L3 二次确认 + 参数清洗管线**                                           |

- **能借鉴（低成本、收益高）：元认知工具。** 给模型一个**显式的"我卡住了"出口**：
  - `halt_task`：主动终止并说明原因（现在模型只能靠"不调工具"来收尾，语义含糊）；
  - `think`：允许一次"只想不做"的推理轮（对本地小模型尤其有用——它经常需要一个不产出工具调用的思考轮来整理线索）。  
    两者都定级 **L0**（纯本地、无网络），不走风险闸门，实现量与现有的 `note_fact` 相当。
- **别抄**：把 `shell_exec` / `python_exec` 直接暴露给模型且不做分级。**本项目的 L3 二次确认 + 白名单是相对优势，不要为了"更强"而降低它。**
- 对比视角：鸾鸟用"建议你在容器里跑"来解决高权限工具的爆炸半径；本项目用"应用层分级闸门"解决同一个问题——后者对单机用户更可落地。

## 6. 持久化与人机协同

|      | 鸾鸟                                                         | 本项目                                    |
| ---- | ---------------------------------------------------------- | -------------------------------------- |
| 进程   | **双进程**：Web 监控台（独立服务）+ Agent 工作进程，靠 SQLite `luan1ao.db` 通信 | **单进程** FastAPI + SQLite + SSE 实时推送    |
| 可视化  | 任务图 DAG 实时演化，可点节点看该子任务的日志/产出物                              | 对话树「线索分支」小地图 + 报告面板                    |
| 人机协同 | **HITL**：计划生成后暂停等审批，可**编辑计划 JSON**、可**注入新子任务**             | 逐步确认（`approved: true/false`），无"改参数再执行" |

- **能借鉴（低成本）**：会话级**复盘视图**。本项目每步都已落库（`steps` 表），再补一个"本任务 token / 耗时 / 失败归因分布 / 情报增量"的汇总，就能回答"这一轮到底白干没有"——这正好是 `dig-scope-workflow` §2「空转判定」所需要的客观数据。
- **能借鉴（中等成本，对 L2 特别有用）**：把确认粒度从"是/否"扩到"**可改参数后执行**"。模型给 L2 工具的 `args` 常常只差一点（比如少写一个 `-e php`），现在只能拒绝后重来一轮（浪费一整轮预算）。
- **别抄**：双进程 + 图可视化（依赖图结构）。

## 7. 提示词工程 ← 差距第二大的层

|    | 鸾鸟                                                                                                                                                                                                                                                                                                                                        | 本项目                                                                               |
| -- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 组织 | **jinja2 模板系统**：`core/prompts/manager.py` + `renderers.py`；zh/en 双语言各一套；`common/` 下公共片段可复用（`tool_selection_guide` / `failure_attribution_levels` / `vulnerability_testing_guide` / `response_analysis_framework` / `filter_bypass_methodology` / `node_type_guide` / `causal_graph_summary` ...）；每个角色独立模板 + 独立的 `output_schemas/*.jinja2` | 单个 `SYSTEM_PROMPT` 字符串常量（约 2.6KB），运行时用 `+` 拼接上下文（项目信息 / 情报 / 事实 / 线索树 / reminder） |

- **能借鉴（性价比高）：把 SYSTEM_PROMPT 片段化。** 按职责拆成可组合的片段——红线 / SOP / 工具清单 / 知识库纪律 / 报告闸门 / 失败归因——再按任务模式（自由跳 vs 锁面）组合注入。  
  好处：改一处不会碰坏另一处；现在这个 2.6KB 常量每加一条都要担心影响别处（事实上本轮加红线时就要额外确认不引入 `{}` 破坏 `.format`）。
- **别抄**：zh/en 双语 + 完整模板引擎（本项目不需要 en，引入 jinja2 只增加依赖与排查成本）。用 `str.format` 或分段常量列表即可。

## 8. 结论：按性价比排序的落地清单

> **实施进度（2026-09-15）**：第 1–4 项**已实现并通过验证**——详见 README「长任务稳定性」一节，  
> 以及 `app/config.py` 新增的配置项与 `app/agent.py` 的 `_compress_history` / `_attribute_failure`。  
> 第 5–9 项尚未做。

| # | 措施                                         | 成本 | 收益               | 是否需要强模型 | 状态                                 |
| - | ------------------------------------------ | -- | ---------------- | ------- | ---------------------------------- |
| 1 | **机械式上下文压缩**（保留近 N 轮 + 旧 tool 消息压成一行）      | 小  | 直接缓解"十几轮后开始忘事"   | 否       | ✅ 已实施（24 条触发 / 保留 12 条 / 每条 300 字） |
| 2 | **失败归因三分（L1/L3/L4）写进回喂内容**                 | 小  | 直接降低"连续 3 次失败就停" | 否       | ✅ 已实施（并多加一档 `SCOPE`= 被白名单拒绝，必须停手）  |
| 3 | **失败阈值语义改为"先换策略，再停止"**                     | 极小 | 同上，几条代码          | 否       | ✅ 已实施（3 次要求换策略 / 6 次才停止）           |
| 4 | **会话级 token 熔断**                           | 小  | 云端供应商的钱包保险       | 否       | ✅ 已实施（按「单次任务累计」计，默认 80 万 token）    |
| 5 | **`halt_task` / `think` 元认知工具（L0）**        | 小  | 给模型"卡住了"的显式出口    | 否       |                                    |
| 6 | **SYSTEM_PROMPT 片段化**                      | 小  | 可维护性，降低改一处的回归风险  | 否       |                                    |
| 7 | **会话复盘视图（token/耗时/归因/情报增量）**               | 中  | 让"空转判定"有客观依据     | 否       |                                    |
| 8 | **确认粒度扩到"可改参数后执行"**                        | 中  | 省下一整轮预算/次        | 否       |                                    |
| 9 | **`EXECUTION_MODE` 式消融开关**（本地单步 / 云端多步可切换） | 中  | 云端路由时释放能力        | 部分      |                                    |

**不建议现在做**：DAG 任务图、P-E-R 三角色、因果图谱（`Evidence→Hypothesis→Vulnerability→Exploit` + 置信度 + `FALSIFIES` 边）。  
它们的**前提**是：模型能稳定产出结构化 JSON、且单任务预算能支撑 50 轮 × 全图上下文。本项目当前定位是"本地优先、离线可用"，直接搬过来会得到一台"没油的车"。

**什么时候再回头看 P-E-R**：当你把默认决策模型稳定切到经过 function calling 验证的云端模型（你的 `providers.py` 已支持 DeepSeek / Claude 等），并且接受单任务 50 次调用量级的成本时——那时值得做的也不是"抄图谱"，而是**先把 §1 的消融开关做出来，用你自己的目标逐项对比单步与多步的成功率**。鸾鸟作者自己就是这么干的（它内置了 `react` 模式做对照）。
