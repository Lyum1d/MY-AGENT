> 白盒**怎么读命中**（分类篇）。检索层给你一堆 `文件:行号`，**那全是候选不是漏洞** —— 本篇讲怎么把命中分成「真候选 / 需补链 / 已知误报」三类，以及每条规则大概能信到几分。查完怎么走流程见 `whitebox-audit-method`。
> 一句话：**`sink` 命中只说明「这里有个危险调用」，不说明「有漏洞」。**

# Sink 命中分类手册

## 一、规则库的全貌（用来估"我是不是漏看了"）

| 语言 | 条数 | 抽取方式 |
|---|---|---|
| `php` | 17 | 词法（lexical） |
| `javascript` | 16 | 词法（lexical） |
| `python` | 14 | **AST（精确）** |
| `java` | 13 | 词法（lexical） |
| `*`（通用，跨语言） | 3 | 词法 |
| **合计** | **63** | |

⚠️ **只有 Python 走 AST**（Python 有内置 `ast` 模块）。其余语言是**词法抽取** —— 每条命中会带 `extractor` 字段，**看到 `lexical` 就要多想一步**：它认不出「这行在注释里」也认不出「这个字符串是给人看的文案」。

### ⚠️ `@taint` / `@runner` 后缀 = **证据强度更低**的另两类命中

`rule_id` 带后缀表示这条命中**不是**行级直接看到的，而是靠**同一函数内的追踪**推出来的：

| 后缀 | 通道 | 形态（看 `why`/`hint` 已写明） | `extractor` | 该怎么对待 |
|---|---|---|---|---|
| （无） | **行级** | 这一行本身就危险：`executeQuery("..." + param)` | `lexical` / `ast` | 正常走 Phase 3 |
| `@taint` | **跨行污染** | **危险值**在别处拼好，这里只把变量传进来 | `taint(lexical)` | **先往上读那个变量的赋值行**，确认它确实由外部输入拼成 |
| `@runner` | **执行器变量** | **执行器**在别处取得（`Runtime r = Runtime.getRuntime()` → `r.exec(...)`） | `runner` | **往上读赋值行**确认执行器来源，再判参数是否可控 |

```java
String sql = "{call " + param + "}";      // ← 危险在这里（上一行）
stmt = conn.prepareCall(sql);            // ← @taint 命中打在这一行

Runtime r = Runtime.getRuntime();        // ← 执行器在这里取得
Process p = r.exec("echo " + param);     // ← @runner 命中打在这一行
```

⚠️ 三个通道**可能同时命中同一行** —— 不是重复，是**性质不同的线索**。

⚠️ **两个间接通道各自只覆盖 4 条 / 1 条规则**：
`@taint` 只在 `java.rce.runtime_exec` / `java.sqli.concat` / `java.path.file` / `java.ssrf.url`
（`call_pattern` 非空）；`@runner` 只在 `java.rce.runtime_exec`（`runner_pattern` 非空）。
**别的规则没有这些通道**，对应写法在其他 kind 上仍会漏（**已知边界，不要当成"规则坏了"**）。

⚠️ **`@runner` 为什么不做成「放宽正则 `\.exec\(`」**：那会匹配**任意对象**的同名 `exec`，
是裸奔。正确做法是**变量层面的类型判定** —— 只有调用者确实来自 `Runtime.getRuntime()` /
`new ProcessBuilder(...)` 才算。**命中数少，但每条都可信。**

**13 个 `kind`**（用 `code_search sink <kind>` 收窄）：

| kind | 条数 | 一句话 |
|---|---|---|
| `rce` | 17 | 命令/代码执行、文件包含、动态调用 |
| `deserialization` | 7 | 反序列化 |
| `path_traversal` | 7 | 路径穿越、文件读写 |
| `sqli` | 6 | SQL 注入（含 NoSQL） |
| `xss` | 6 | 输出未转义 |
| `weak_crypto` | 5 | 弱算法、不安全随机 |
| `ssrf` | 4 | 服务端请求伪造 |
| `hardcoded_secret` | 3 | **通用规则**，硬编码凭据 |
| `ssti` | 2 | 模板注入 |
| `auth_bypass` | 2 | JWT/鉴权绕过 |
| `debug` | 2 | 调试开关、调试输出 |
| `open_redirect` | 1 | 开放重定向 |
| `xxe` | 1 | XML 外部实体 |

⚠️ **某语言没有某 kind 是常态，不是缺口** —— 比如 Java 没有 `hardcoded_secret`（由通用规则覆盖）、PHP 没有 `xxe`。**判断"有没有漏"要看 kind 覆盖，不要按语言数条数。**

## 二、命中的三类归宿

拿到一条命中，**先分类再动手**：

### 第 1 类：**真候选**（值得立刻读上下文）

特征：
- `kind` 是 `rce` / `deserialization` / `sqli` 这类**直接危险**的；
- `why` 里没有"宽口径"这类自我限定；
- 命中所在行**明显在处理外部输入**（`$_GET` / `request.args` / `@RequestParam`）。

动作：`code_read <codebase_id> <file>:<line> 30` 读上下文 → 走 Phase 3 逆向。

### 第 2 类：**需判定层补链**（命中本身不完整）

特征：
- 命中在**输入采集文件**里，但 sink 在**另一个文件**；
- `scope` 为空且文件通篇没有函数定义（**include 片段**，DVWA 的 `source/*.php` 就是这样）；
- `kind=xss` 但所在行拼的是**数据库结果变量**（而非超级全局变量）。

⚠️ **这一类不是"规则漏了"，是架构使然** —— 详见下节。**别去放宽规则硬凑。**

### 第 3 类：**已知误报形态**（单列，不掩盖、不阻塞）

特征：
- `why` 里**自己写着**"宽口径"（如 `php.xss.echo_var`）；
- 命中在**测例 / 文档 / 注释**里；
- 命中在**安全实现版**里（下节的 `impossible.php`）。

动作：**记下来但别当洞**。这类要做的是**累积成负样本**去守回归，而不是改规则把它盖掉。

## 三、⭐ 两条 DVWA 实测得来的硬结论

### 结论 1：期望值**按「sink 在哪」写，不按文件名写**

DVWA 采用**输入/输出分离**架构：`fi` 模块的输入在 `source/low.php`（只有
`$file = $_GET['page'];`），**sink 在 `fi/index.php:36`（`include( $file );`）**；
`xss_s`（存储型）的输出点拼的是**数据库结果变量**、不在 `source/` 里。

**教训**：拿 `source/low.php` 当期望位置，会得出"工具没打中"的**错误结论** —— 实际是**期望写错了**。

⚠️ **跨文件链路是判定层（模型）的活**，与 §4.1「检索层不做跨文件数据流」的分工一致。
**靠放宽规则去凑跨文件命中，会让整个仓库疯狂误报。**
**已知边界（不是 bug）**：存储型 XSS 的输出点常常命不中（拼的是数据库结果变量，没有超级全局变量）。

### 结论 2：**`impossible.php` 是现成的真实负样本**

DVWA 每个模块自带一份 **`source/impossible.php` = 安全实现版** —— 比手工编负样本更可信的 ground truth。

⚠️ **但用它做负样本必须限定文件范围**：整个仓库别处当然会命中这些规则（实测 237 处），
不限定范围的话负样本**永远"失败"**，等于没测。这是召回基准里 `forbid_in` 字段的由来。

**推广**：验证"规则是否误报"**不要**拿全仓库当负样本，要**挑出明确安全的那个文件/版本**。

## 三·五、⭐ 真实项目上的召回（OWASP BenchmarkJava 实测）

⚠️ DVWA 上的 100% 召回**不能信** —— 规则就是**照着那个形态调的**（拼接与 sink 同行）。
换到真实项目会**大幅下降**。这是本能力最重要的一条认知。

⚠️ **先看分母口径**（v071 更正，这条比数字本身重要）：真实评测集的检出常常是
**部分的**（本机 669 个 `BenchmarkTest*.java` vs CSV 的 **2740 条**标注），
**73% 的真漏洞标注在本机没有源码**，结构上不可能命中 —— 算进分母会把召回**压成四分之一**。
正确分母是「标注 ∩ 检出」：按此口径 5 个有规则的类别合计 **176/212 = 83.0%**
（`cmdi`/`crypto`/`hash`/`pathtraver` 均 **100%**，`sqli` **43.8%**）。

**教训**：**标尺本身也会错**。看到「召回很低」先别急着改规则 ——
先确认分母是不是把"本机根本没测到的用例"也算进去了。

⚠️ **别把 100% 读成"规则很完美"**：它只说明**这几个 kind 的规则覆盖了本机所有可命中的
该类别用例**，不代表规则精确 —— 且精确性**不判数据流**：安全变体与漏洞变体常常只差
「参数是否真的可控」，规则命中它们是对的，要模型往上读才能定论。

⚠️ **精确性也会被口径骗**：`crypto` 一度显示 **51%**（看着像疯狂误报），
拆开才发现那 35 个"误报"**根本不是 crypto 规则报的** —— 是别的规则在同一文件里命中，
被算到了它头上。按 kind 归因后 **51% → 100%**。
**"别类规则的命中"不是"本类规则的误报"** —— 与「没测 ≠ 0 分」（v067）同族：
**用一个不成立的归属去算指标。**

### 漏在哪：四种结构性原因（按影响排序）

1. **跨行污染** —— 拼接与 sink 不在同一行。已补（`@taint`），4 条规则有。
2. **调用者变量** —— `Runtime r = Runtime.getRuntime(); r.exec(cmd + param);`
   旧的字面量 pattern 一个都匹配不到。**实测 cmdi 这类占 27/35**。已补（`@runner`），1 条规则有。
3. **全限定名** —— 真实 Java 代码大量写 `new java.io.FileInputStream(...)`，而规则早期只认短名。Benchmark 全库：`new java.io.File*` **522 处**、短名只有 **18 处**。**不修等于放掉 97%。**
   - 推广：**任何语言的规则都要问一句「真实代码会不会写全限定名 / 带命名空间」**（Java 的 `java.io.`、Python 的 `os.path.`、PHP 的 `\Foo\Bar`）。
   - ⚠️ 但**别修过头**：放宽成 `new\s+[\w.]+\s*\(`（任意类名）会把 `new ArrayList(` 全收进来，误报爆炸。要**逐类显式枚举**。
4. **容器/间接传递** —— `argList.add("cat " + param)` → `pb.command(argList)`。污染进了容器对象，靠"变量名匹配"追不到。**已知边界，尚未做。**


### 还有一类漏报是**判定层的活，不是规则的事**

Benchmark 的 sqli 用例常见 `param = values[0]`（数组下标取值）→ 属**数组传播**，
在污染分析的**能力范围之外**（有意不做）。这类要**靠模型读上下文**补 ——
与「跨文件链路归判定层」同一条纪律。

## 三·六、⚠️ 别信"命中总数"

实测抓到过两个「看起来能打、实际完全没工作」的陷阱：

1. **宽口径伪命中**：`\.load\s*\(`（匹配任何 `.load(`）在 Benchmark 上产出 45 处命中，
   **绝大多数是 `Session.load()` / `config.load()` 之类的误报**，只是混在总数里被 kind 分布掩盖了。
2. **死代码通道**：「跨行污染」第一版把判据挂在"行级没命中"的分支上 → **整层从未生效**
   （`extractor` 里一个 `taint` 都没有，而总数看着还在涨）。

**教训**：看到「命中数变了」，**先按 `rule_id` / `extractor` 拆开看**。**总数是个会骗人的指标。**

## 四、逐条读命中的字段

```
code_search <codebase_id> sink rce php        # 收窄到 rce + php
```

| 字段 | 怎么读 |
|---|---|
| `file` / `line` | **证据链唯一合法来源**。禁止凭记忆写行号 |
| `kind` | 上表 13 类之一 |
| `rule_id` | 精确到规则。**同类里不同 rule_id 的宽窄度可能差很多** |
| `why` | **先读这里** —— 规则作者会写清它的取向；出现"宽口径"就降预期 |
| `hint` | 该看什么（如"追这个变量能否到请求参数"） |
| `scope` | 所属函数。**空 scope 且文件无函数定义 = include 片段，正常** |
| `extractor` | `lexical` 需人眼复核；`ast` 精确（见上表三个通道） |

### 已知需要额外小心的几条

| rule_id | 问题 | 处理 |
|---|---|---|
| `php.xss.echo_var` | **宽口径**：匹配"变量输出到页面"，真 XSS 只占一部分 | 追变量来源；**留着是因为存储型输出端没它就全漏** |
| `java.xxe.factory` | 报的是"解析 XML"，**默认配置下**才可能允许外部实体 | 必须查有没有关掉 DTD / 外部实体 |
| `js.xss.react_dangerous` | `dangerouslySetInnerHTML` **名字就说明了它在做什么** | 查传入的 html 是否可能含用户输入 |

## 五、正向：什么样的命中**基本可以排除**

| 形态 | 为什么安全 |
|---|---|
| `execute(?, [$name])` / `execute([$name])` | **参数化绑定** —— 值不参与 SQL 解析 |
| `htmlspecialchars($x)` / `htmlentities` / `urlencode` / `strip_tags` / `filter_var` | 转义/过滤；**注意要同行**才被规则黑名单认到 |
| `subprocess.run([...])` 列表传参 | 无 shell 解析 |
| `yaml.safe_load` / `JSON.parse` | 安全反序列化 |
| `secrets.token_*` / `os.urandom` | 密码学安全随机 |
| `prepare` / `bindParam` | 预处理语句 |

⚠️ **"用了净化函数"≠"净化对了"**：`intval` 挡不住字符串上下文注入、`addslashes` 挡不住 GBK 宽字节、`htmlspecialchars` 不传 `ENT_QUOTES` 挡不住单引号属性。**要看清净化的语义与它的调用上下文。**

## 六、一页速查

| 你看到的 | 它是什么 | 该怎么办 |
|---|---|---|
| `rule_id` 带 `@taint` | **跨行证据**（危险值在上方赋值拼好） | **先往上读赋值行**，再判可达性 |
| `rule_id` 带 `@runner` | **执行器证据**（`r = Runtime.getRuntime()` → `r.exec(...)`） | **往上读赋值行**确认执行器来源，再判参数可控性 |
| 报告写「本机检出是部分的」 | 评测集只检出前一段 | 召回按「可命中」分母读，**别按标注总数读** |
| 报告里精确性标「文件级 xx%」 | 那个口径混了别类规则的命中 | 以 **kind 级主值**为准 |
| `why` 写"宽口径" | 规则自己在提示会误报 | 追数据来源再定 |
| `scope` 为空 + 文件无函数 | include 片段 | **正常**，不是漏抽 |
| 输入在一个文件、sink 在另一个 | 输入/输出分离架构 | **判定层补链**，别放宽规则 |
| 真实代码写全限定名（`java.io.File`） | 曾是**全库级盲区**（522 处） | 已修；遇到别的语言先想这一步 |
| `impossible.php` 里命中 | 安全实现版 | 拿去当**负样本**（配 `forbid_in`） |
| 命中在测例/文档/注释里 | 噪音 | 单列，不阻塞 |
| **总数变好看/变难看** | 可能只是宽口径规则在抖 | **按 `rule_id`/`extractor` 拆开看**，别信总数 |
