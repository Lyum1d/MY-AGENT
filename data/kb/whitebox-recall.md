> 白盒**召回怎么读**（召回篇）。姊妹篇：`whitebox-targeting`（**打哪个目标**）、`whitebox-audit-method`（**拿到代码之后怎么审**）、`whitebox-sink-triage`（**命中怎么分类**）。
> 一句话：**召回数字本身也会骗人** —— 先确认**分母**、再确认**口径**、最后才看结果。

# 白盒召回：口径、实测与漏报归因

## 一、读召回前必须确认的三件事（顺序不能换）

⚠️ **这三个问题任何一个没答，数字就不能用。**

### 1. 分母是什么？

⚠️ DVWA 上的 100% 召回**不能信** —— 规则就是**照着那个形态调的**（拼接与 sink 同行）。换到真实项目会**大幅下降**。

⚠️ **先看分母口径**（v071）：检出常常是**部分的**（本机 669 个 `BenchmarkTest*.java` vs CSV **2740 条**标注），**73% 标注本机没源码** —— 算进分母会把召回**压成四分之一**。正确分母 =「**标注 ∩ 检出**」。
⚠️ **口径漂移的代价**：同一份代码，按旧口径（标注总数当分母）读出的是 **20.4%**，按正确口径读是 **70.8%**（v086）。**数字差 3 倍，代码一行没改。**

### 2. kind 级还是文件级？

⚠️ **（v072）** `crypto`/`hash` 共用 `weak_crypto`，文件级**100%** 里一半是**别类规则凑的**；按本类别规则只有 **51.4% / 73.7%**。**两个口径并排时读者会默认它们同口径 —— 比只显示一个更误导。**

### 3. 精确性的误报是谁报的？

⚠️ **精确性也会被口径骗**：`crypto` 一度显示 **51%**，拆开才发现那些"误报"**不是 crypto 规则报的**，是别类规则在同一文件里命中、被算到它头上；按 kind 归因后 **51% → 100%**。

⭐ **总教训**：**标尺本身也会错**。看到「召回很低」先别改规则，先查分母是不是把"本机没测到的用例"也算进去了。
⚠️ **别把 100% 读成"规则完美"**：它只说明**本机可命中的同类用例都被覆盖**，不代表精确 —— 且规则**不判数据流**：安全/漏洞变体常只差「参数是否可控」，要模型往上读才能定论。
**"别类规则的命中"不是"本类规则的误报"** —— 与「没测 ≠ 0 分」（v067）同族：**用一个不成立的归属去算指标。**

### 4. 你**自己写的探针**有没有真的在测东西？

⚠️⚠️ **（2026-10-06 实测）** 一个临时探针报「**cmdi 只有 22.9%**」，与项目 harness 的 **100%** 打架。
**查清后：探针错了，引擎没错。**

根因：规则对象上 `call_regex` / `regex` 是**惰性编译的方法**（`SinkRule.call_regex`），**不是字符串**。
探针写成 `re.search(r.call_regex, src)` —— 把 **bound method** 当 pattern 传进去，**每条规则都抛
`TypeError: first argument must be string or compiled pattern`**，又被 `except` 吞掉 → **全部记 0**。
正确写法是**调用它**：`pat = r.call_regex; re.search(pat() if callable(pat) else pat, src)`。

⭐ **量出来的是 22.9%（8/35），真值是 100%（35/35）—— 差的 27 处全是「调用者变量」形态**
（`Runtime r = Runtime.getRuntime();` + 下一行 `r.exec(...)`），**正是 §三第 3 条 `@runner` 通道早就接上的那批**。
两通道实测**完全互补**：`call` 命中 8、`runner` 命中 27、**重叠 0、漏 0**。

**两条教训**：
1. **「我的探针」与「项目 harness」打架时，先怀疑探针** —— 本项目已发生**两次**
   （v060/v064「工具写错时，它造成的破坏会被误当成被测代码的问题」、本次）。
2. **静默的 `except` 会把「测不了」伪装成「测到了 0」** —— 探针**必须打印异常**，
   否则 0 分和「一条都没命中」长得一模一样。这与 v072「死代码通道让总数变好看」同族。

⚠️ **另外**：这 27/35 早在 §三第 3 条就写明了，**我却当成新发现重新推了一遍** ——
**动手前先读 KB 的「漏在哪」一节**，可省一整轮。

## 三、漏在哪：七种结构性原因（v086 起，v090 补两条）

> ⚠️ **第 8 条在别处**：**调用名白名单覆盖**（v091，21 例 sqli 漏报）属"规则覆盖"，见 `whitebox-sink-triage` §一。

1. **控制流前缀赋值**（v086 补）—— `if (cond) x = ...` / `} else { x = ...` 这类**整行**被 `_ASSIGN` 的 `^\s*` 锚点吞掉 → 变量永不进污点集。**实测占当时 sqli 漏报真漏洞的 56%（24/43）**，是当时**最大的单一根因**。
   修法**刻意不对称**：右值脏 → **标脏**；右值安全 → **不清除**（分支执行与否词法层判不出，清除=制造不可恢复的漏报）。
   净收益 sqli **39.1% → 46.9%**，其余四类**一文未动**（见「改动后必须按 rule_id 拆开比对」）。
   ⚠️ **v090：这条判据当时被绕过了一半** —— 见下面第 6 条。**修好一处不等于这条规则处处生效。**
2. **跨行** —— 拼接与 sink 不在同一行。**调用侧** v069 已补（`@taint`，4 条规则有）。
   ⚠️ **v090 更正口径**：待办里那条「多行**调用**是缺口（15/104 = 14.4%）」量错了对象 ——
   调用侧 v069 早就修好了（34 例漏报里只有 **3 例**含这种调用点）；**真缺口在赋值侧**（第 7 条）。
   ⭐ 教训：**"多行"很含糊，量之前要说清是"多行调用"还是"多行赋值"。**
3. **调用者变量** —— `Runtime r = Runtime.getRuntime(); r.exec(cmd + param);` 旧的字面量 pattern 全都匹配不到。**实测 cmdi 占 27/35**。已补（`@runner`）。
4. **全限定名** —— 真实 Java 大量写 `new java.io.FileInputStream(...)`，规则早期只认短名。全库 `new java.io.File*` **522 处**、短名仅 **18 处**。**不修等于放掉 97%。**
   - 推广：**任何语言都要问「真实代码会不会写全限定名」**（Java `java.io.`、Python `os.path.`、PHP `\Foo\Bar`）。
   - ⚠️ **别修过头**：放宽成 `new\s+[\w.]+\s*\(` 会把 `new ArrayList(` 全收进来。要**逐类显式枚举**。
   - ⚠️ **同一个盲区会在多层各犯一次**（v072）：v069 修的是规则 `pattern` 层，`taint.py` 的 `_ASSIGN` 与 `_lhs_name` **两处都不允许类型名带 `.`** → 全限定声明的变量**从没进污点分析**（影响 591 行）。**修一处后要问「同类判据还有几处」。**
5. **容器/间接传递** —— `argList.add("cat " + param)` → `pb.command(argList)`。污染进了容器对象，靠"变量名匹配"追不到。**已补容器 `add` 通道**（v072），但**增量 0**：`ProcessBuilder(` 的 pattern **不关心括号里是什么**，那行早就命中了 —— **修的是正确性，不是召回**。
6. **控制流前缀被当成左值 → 反过来"清除"污点**（v090 补，第 1 条的**反面**）—— `_ASSIGN` 的「带类型声明」分支字符类**不含括号**，
   所以 `if ((500 / 42) + num > 200) bar = param;` 匹配失败 → 走 `_PREFIXED_ASSIGN`（v086 判据）✓，
   而 `else bar = "This should never happen";` **不含括号 → 被 `_ASSIGN` 吞下**，抠出的左值是 `else bar` → 走「**覆盖即净化**」✗。
   **恰好绕过 v086 刻意设计的不对称判据**：刚标的脏被下一行的"安全分支"清掉 → 变量退不回污点集。
   **实测 `BenchmarkTest00606` 因此漏报**（`executeUpdate(sql)` 判不出污点）。修法：这类行交回不对称判据（脏→标脏；安全→不清除）。
   ⚠️⚠️ **不许"整个忽略"这类行** —— 那会同时丢掉 `else bar = param;` 该标的脏。**v090 第一版就是这么写的**，
   结果**误报与召回同时下降**；而"只加污点"**不可能**让误报下降 —— 这个矛盾当场暴露它是**用一个回归换来的假收益**。
   ⭐ 可复用的判据：**改引擎时，若两个指标朝"不该动"的方向一起变，先怀疑改动本身，不要庆祝。**
7. **跨行赋值**（v090 补）—— 左值与 `=` 在本行、右值在**续行**：
   `bar =` ⏎ `new String(...Base64.encodeBase64(param.getBytes())));`
   `_ASSIGN` 的右值要求 `.+?`（至少一字符），于是 `bar =` **整行匹配失败** → 续行里的污点变量看不见 → 变量**从未被判脏**。
   **实测 `BenchmarkTest00604` 因此漏报**。修法：往后并几行直到 `;` 再判（`_ASSIGN_LOOKAHEAD = 6`）。
   ⚠️ **跨行不是"不清除"的免责理由**：续行右值若真的安全，**仍须清除**（直线代码无分支歧义）—— `test_090` 专门钉了这条。

## 四、⚠️⚠️ 「数组传播」不是独立缺口（v086 实测**推翻了旧判断**）

长期待办里写着「`param = values[0]` 属数组传播，是 Benchmark sqli 的主力漏报形态」。**v086 去量了，它不成立**：

| 测法 | 结果 |
|---|---|
| 「右值 = 已有变量`[下标]`」且基变量已污点、左值却没接上的 | **0 处** |
| 「右值 = 变量`[下标]`」总计 | 225 行，**225 行全部正常传播** |
| 粗筛出的「判不脏」261 行 | 绝大多数是 `new byte[N]` **数组分配**（本就不该脏） |

原因：`_names()` 抠的是**标识符**，`values[i]` 里的 `[i]` 不参与 —— 「容器脏 → 下标取值也脏」**现成就能工作**。
那批漏报里被标成「数组」的 19 个，**真正的断点在上游**：`if (values != null) param = values[0];` 整行被锚点吞掉，**是第三节第 1 条问题，不是下标语义问题**。**一个标签把两个根因混在了一起。**

⭐ **教训：待办里那条是「推断」，不是「测量」。一旦去量，它就让位给了更靠前、更朴素的根因。**
**排优先级前先量** —— 否则会花大力气去打破一条「有意边界」，去修一个并不存在的缺口。

## 五、⚠️ 已知最大缺口（**有意不修**）

### 控制流分支不合并（v072 查明）

`taint` 是**直线分析**，`switch`/`if` 的**最后一次赋值**说了算。Benchmark **129 个用例**用 `switch` 形态：`case 'A': bar = param;` … `default: bar = "常量";` → 本层在 `default` 把 `bar` 清掉 → 真漏洞漏判。

**为什么不能简单取并集**：漏洞变体用 `guess.charAt(2)`（走 `case 'C'` → `bar = param`），安全变体用 `guess.charAt(1)`（走 `case 'B'` → `bar = "常量"`），**两者 `switch` 段逐字节相同**，全库 `charAt(2)` vs `charAt(1)` 各 **26** 个（**几乎 1:1**）。取并集会**同时**捞回 ~26 个真漏洞、**同时**制造 ~26 个误报 → **净收益近零**。要判对必须**常量折叠**，超出本层能力 —— **属判定层（模型）的活**。

⚠️ **注意与第三节第 1／6 条的区别**：v086/v090 修的是「**带前缀的赋值整行看不见**」与「**反过来被清除**」
（纯遗漏/纯误清除，修了只有好处）；这里说的是「**分支语义判不对**」（取并集有对称代价，所以不修）。
**三件事长得很像，性质完全不同** —— v090 实测：剩下 10 例 sqli 漏报里 **9 例**属于本条（`switch` 形态）。

### ⚠️ 别信"命中总数"（v072）

两个「看起来能打、实际没工作」的陷阱：① **宽口径伪命中**（`\.load\s*\(` 产 45 处多数是误报，混在总数里被 kind 分布掩盖）；② **死代码通道**（跨行污染第一版判据挂在"行级没命中"分支上 → 整层从未生效，`extractor` 里一个 `taint` 都没有，总数却还在涨）。

**两个方向都会骗人** → 改动后**必须按 `rule_id`/`extractor` 拆开比对**。
⭐ **v086 的实际做法可照抄**：改 `taint.py` 后用 `git stash` 取旧版，对**全库 7 条 java 规则**跑两遍画像，实测「`java.sqli.concat@taint` 34 → 43，**其余 6 条 Δ=0**」—— **这才叫"净收益"，不是"总数涨了"。**
⭐ **v090 用它抓到了一个假收益**：第一版实现让**误报降、召回也降**；而"只加污点"**不可能**降误报 ——
这个矛盾说明那个"收益"是**牺牲召回换来的**。**两个指标朝坏方向一起动时，先审改动，别庆祝。**

|---|---|---|
| 一个召回数字 | 分母是不是「标注 ∩ 检出」？ | 本文 §一 |

| 「要改规则提召回」 | 先量净收益（`git stash` 对照，按 rule_id 拆开） | 本文 §五 |
